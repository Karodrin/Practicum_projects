1. Провёл анализ требований на наличие серых зон количестве 19 позиций, числе рабочих допущений 2 позиции и проработал их. Что в итоге снизило риск разночтений при реализации функционала и уменьшило количество спорных дефектов.
2.Выполнил комплексную проверку по чек‑листу(58 выполненных тест‑кейсах, покрывающих 19 ключевых пользовательских сценариев), расставив приоритеты проверок в зависимости от меток регресса и критичности для текущего релиза. Что в итоге для команды — ускорило выявление блокирующих дефектов до релиза; менеджеру — дало прозрачную картину готовности функционала под релиз.
3. Составил чек‑лист для смоук‑тестирования из 7 проверок, покрывающий базовый функционал продукта. В итоге это позволит QA‑инженерам быстро подтверждать работоспособность сборки перед каждым релизом, сократив время на предварительную проверку
4. Сделал оформление всех выявленных несоответствий в виде структурированных баг‑репортов с шагами воспроизведения, ожидаемым/фактическим результатом и приложенными артефактами.
5. Создал таблицу валидации в количестве 7 полей, применив техники классов эквивалентности и граничных значений выделил 80 КЭ и 56 ГЗ (С учётом оптимизации повторяющихся значений) для полей формы регистрации. Что в результате даёт готовую основу для проектирования тест‑кейсов, что повысило полноту покрытия проверок и снизило риск пропуска ошибок валидации.
6.Сделал заполнение итоговой сводки по результатам тестирования с разделением проверок по статусам, выделил критические баги и оформил вывод о готовности релиза по результатам проверки.
При выполнении проекта я использовал: Figma, Android Studio, DevTools, Postman, DBeaver, Swagger, SQL-запросы, Тест-анализ, Тест-дизайн, Регрессионное тестирование, Кроссбраузерное тестирование, Smoke-тестирование, Функциональное тестирование.
